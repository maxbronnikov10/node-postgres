---
title: pg.QueryExecutor
---

`QueryExecutor` runs concurrent independent SQL statements over a bounded set of
JavaScript clients. Connections open lazily. Each connection pipelines queries,
with a separate protocol synchronization boundary for each statement.

```ts
import { QueryExecutor } from 'pg'

interface User {
  id: number
  name: string
}

const executor = new QueryExecutor({ connectionString: process.env.DATABASE_URL })

try {
  const users = await Promise.all(
    [1, 2, 3].map((id) => executor.maybeOne<User>('SELECT id, name FROM users WHERE id = $1', [id]))
  )
  console.log(users)
} finally {
  await executor.end()
}
```

Type declarations ship with the package for CommonJS and ESM. TypeScript checks
your code against the row shape you supply. `Client`, `Pool`, `Query`, `Result`
and the independent-query engine are implemented in strict TypeScript; JavaScript
applications use the compiled runtime through the existing package entrypoints.

This API is available from the CommonJS and ESM JavaScript exports, together with
`QueryExecutorError`. It is not part of `pg.native`. Construction requires a runtime
providing `events.addAbortListener`; otherwise it throws `PG_EXECUTOR_UNSUPPORTED`.
Ordinary `Client` and `Pool` do not acquire this requirement.

## new QueryExecutor

`new QueryExecutor(options?)`

Accepts [Client connection options](/apis/client#new-client), including connection
strings, TLS, type parsers and prepared-statement options, plus these limits:

| Option                     | Default    | Meaning                                                                        |
| -------------------------- | ---------- | ------------------------------------------------------------------------------ |
| `max`                      | `4`        | Maximum physical frontend connections, including connecting clients.           |
| `maxInFlightPerConnection` | `16`       | Maximum queries assigned to each connection.                                   |
| `maxPending`               | `1024`     | Maximum queries waiting for assignment.                                        |
| `query_timeout`            | `30000`    | Query deadline in milliseconds, including queue and connection wait.           |
| `connectionTimeoutMillis`  | `5000`     | Timeout in milliseconds for each connection attempt.                           |
| `maxMessageSize`           | `16777216` | Maximum inbound message length, including its four-byte length field.          |
| `maxResultRows`            | `100000`   | Maximum rows held across all unfinished application queries.                   |
| `maxResultBytes`           | `67108864` | Maximum result wire bytes held across all unfinished application queries.      |
| `targetSessionAttrs`       | `'any'`    | Required default transaction access: `'any'`, `'read-write'` or `'read-only'`. |

Limits must be positive safe integers. Timeouts must be integers from `0` to
`2147483647`; `0` disables that timeout. Invalid constructor options throw
`QueryExecutorError` with code `PG_EXECUTOR_INVALID`.

The executor manages `pipeline: true` and `autoBatch: false`. An explicit
`pipeline: false` or enabled `autoBatch` is rejected. These defaults are starting
points for application sizing, not universal throughput settings.

The queue is FIFO; assignment chooses the least loaded ready client. Choose limits
appropriate for your parameters and results. An executor belongs to one JavaScript
event loop; limits are not shared across workers or processes.

TLS options retain normal certificate verification. An application may explicitly
share `ssl.secureContext` between connections; see
[TLS connection setup](/apis/client#tls-connection-setup). The executor creates no
implicit TLS context or session cache. Direct TLS negotiation requires a compatible
endpoint.

With transaction-mode PgBouncer, named statements and `maxAutoPrepare` require
compatible protocol prepared-statement tracking, including a nonzero
`max_prepared_statements`. The executor does not make session-scoped SQL `PREPARE`
safe for transaction pooling.

### Endpoint selection and recovery

```js
const executor = new QueryExecutor({
  connectionString: process.env.DATABASE_URL,
  endpoints: [
    { host: 'db-a.example', port: 5432 },
    { host: 'db-b.example', port: 5432 },
  ],
  targetSessionAttrs: 'read-write',
  connectionTimeoutMillis: 2000,
})
```

An explicit `endpoints` list contains 1–64 objects with a required nonempty `host`
and optional integer `port`, `ssl` and `sslnegotiation`. Other keys are rejected.
Connection-string defaults are parsed first, then the endpoint overrides its host,
port and explicitly supplied TLS settings. Shared custom stream/connection instances
cannot be combined with endpoints. Unspecified settings inherit normal Client defaults.

Creation attempts rotate through eligible endpoints. Failures have a brief per-endpoint
cooldown; an uninterrupted outage visits each endpoint once before refusing unsent work.
A later submission can try again. Successful application work permits future recovery
attempts without a background retry loop. Already assigned SQL is never replayed.

For a non-`any` target, the executor runs `SHOW transaction_read_only` before admitting
application SQL. `read-write` requires `off`; `read-only` requires `on`, which also
includes a deliberately read-only primary. Connection timeout includes the probe.
This is a connection-time property, not continuous topology monitoring. A proxy must
route the session to backends with the intended role. A read-only SQL error (`25006`)
on a `read-write` executor poisons that client; the failing statement retains a
server-error outcome and is not retried. Collateral assigned work can be unknown.

Each endpoint retains normal TLS verification against its own hostname. Configure
an explicit certificate identity or CA per endpoint when required; no TLS downgrade
or certificate-verification fallback is performed.

### Inbound message limits

`maxMessageSize` must be an integer from 4 to 2147483647. It caps one backend
message's declared length, including the length field and excluding the tag byte.
Oversized headers and truncated messages close the transport with PG_PROTOCOL_ERROR.
Assigned SQL then has an unknown outcome. A larger explicit cap is available for
large fields. Multiple valid messages can share a chunk whose combined size exceeds
the cap. Use the separate result budgets to bound accumulation across messages.

### Buffered result budgets

`maxResultRows` and `maxResultBytes` are positive safe integers shared by all
unfinished application queries in this executor. RowDescription, DataRow and
CommandComplete frames count toward the byte budget, including each frame's tag
and length word. Each DataRow counts as one row, including nulls and empty fields;
bytes use the original wire encoding, so UTF-8 and binary values retain their
actual byte sizes. Limits are checked before application type parsers and Result
row construction. The protocol's fast text path can already have decoded one
bounded message from UTF-8; rejected frames do not enter the Result.

At a limit, the triggering query rejects with `PG_EXECUTOR_RESULT_LIMIT`, outcome
`'unknown'` and `safeToRetry: false`. The shared connection is discarded, its
assigned siblings also have unknown outcomes, and partial results are released.
Assigned SQL is never replayed. This includes writes with RETURNING: a result
limit does not establish whether the write committed. Other connections can
continue; accepted unsent work can use a replacement connection.

Budget accounting is released on completion, error, cancellation or timeout.
Completed Results held by the caller, input parameters, custom type-parser
allocations and protocol control/error messages fall outside these budgets.
Wire-byte accounting is not a JavaScript heap-size guarantee; the per-message
limit still applies to individual frames. Ordinary Client and Pool behavior is
unchanged.

## executor.query

`executor.query(text, values?) => Promise<Result>`

`executor.query(config) => Promise<Result>`

Returns the usual [Result](/apis/result). Query configuration supports `text`,
`values`, `name`, `binary`, `rowMode`, `types`, `query_timeout` and `signal`.
`text` must be a nonempty string and `values`, when supplied, must be an array.
The values array is copied without encoding parameters until assignment.

Every query uses extended protocol and must contain a single SQL statement,
including queries without parameters. An explicit `queryMode` must be `'extended'`.
Callbacks, custom Query objects, portals, `rows` pagination and per-query transport
options are unsupported.

### Getting rows directly

All four methods accept SQL text with an optional readonly values array, or an
independent-query config object. Each executes one statement once.

| Method             | Return type          | Result cardinality                             |
| ------------------ | -------------------- | ---------------------------------------------- |
| `query<R>(...)`    | `Promise<Result<R>>` | Complete result, including fields and command. |
| `rows<R>(...)`     | `Promise<R[]>`       | All rows; an empty result returns `[]`.        |
| `one<R>(...)`      | `Promise<R>`         | Exactly one row is required.                   |
| `maybeOne<R>(...)` | `Promise<R \| null>` | Zero rows returns `null`; one returns the row. |

`one()` and `maybeOne()` reject unexpected row counts with
`PG_EXECUTOR_ROW_COUNT`, outcome `'unknown'` and `safeToRetry: false`. The check
happens after SQL completes. A write with RETURNING may already have committed;
the helper never repeats it.

```ts
const user = await executor.one<User>('SELECT id, name FROM users WHERE id = $1', [42])
const users = await executor.rows<User>('SELECT id, name FROM users WHERE active = $1', [true])

const tuples = await executor.rows<[number, string]>({
  text: 'SELECT id, name FROM users WHERE active = $1',
  values: [true],
  rowMode: 'array',
})
```

Array mode changes rows into positional tuples. It can reduce object construction
for bulk results; measure it with your column count and workload. PostgreSQL type
parsers and the executor's result budgets apply to both row modes.

Statements must be independent: no transaction control, session `SET`, temporary
table workflows, session locks, COPY or cursors. Use an exclusively checked-out
[Pool client](/apis/pool#poolconnect) for these workflows. SQL is not parsed to
prove independence. If a query leaves a transaction open, the executor discards
that connection and rejects assigned work; this guard does not make session-dependent
queries safe.

### Deadlines and cancellation

```js
const controller = new AbortController()
const result = await executor.query({
  text: 'SELECT id FROM users WHERE email = $1',
  values: ['reader@example.com'],
  query_timeout: 5000,
  signal: controller.signal,
})
```

Per-query `query_timeout` overrides the executor default. Its deadline starts when
`query()` is called and includes time spent queued or waiting for a connection;
assignment does not reset it. Pass an `AbortSignal` to cancel through its controller.
An already aborted signal, queued cancellation or queued deadline prevents dispatch.

After assignment, abort or deadline discards the shared pipelined connection.
Other queries already assigned to that connection can also fail with an unknown
outcome. This is not per-query PostgreSQL cancellation: server-side work may
continue after disconnect. Configure PostgreSQL `statement_timeout` separately
when a server-side execution limit is needed.

## QueryExecutorError

Errors expose `code`, `outcome`, `safeToRetry` and the original `cause`, when present.

| `outcome`        | Meaning                                                               | `safeToRetry` |
| ---------------- | --------------------------------------------------------------------- | ------------- |
| `'not-sent'`     | This attempt was not assigned for dispatch.                           | `true`        |
| `'server-error'` | PostgreSQL returned a statement error; `code` preserves its SQLSTATE. | `false`       |
| `'unknown'`      | Assigned work may have executed, even if completion was not received. | `false`       |

Local errors use `PG_EXECUTOR_INVALID`, `PG_EXECUTOR_OVERLOADED`,
`PG_EXECUTOR_UNAVAILABLE`, `PG_EXECUTOR_CLOSED`, `PG_EXECUTOR_DESTROYED`,
`PG_EXECUTOR_ABORTED`, `PG_EXECUTOR_TIMEOUT`, `PG_EXECUTOR_TRANSACTION` or
`PG_EXECUTOR_RESULT_LIMIT`, `PG_EXECUTOR_ROW_COUNT` or `PG_EXECUTOR_UNKNOWN`. Abort and timeout outcomes depend on whether assignment
has occurred. Collateral failures use a generic transport error, not another
query's abort reason.

The executor never replays assigned queries, including `SELECT`. An unknown outcome
requires application-level reconciliation before retrying writes. `safeToRetry`
is true only for `'not-sent'`; it does not override application retry policy.

If no healthy connection remains after a connection failure, waiting work can
reject as unavailable. `retryAfterMillis`, when present, gives the remaining brief
connection-creation cooldown. Later submissions can reconnect; no hidden query
retry loop runs in the background.

## Counts

- `executor.totalCount`: current connections, including connecting and closing clients.
- `executor.waitingCount`: queries waiting for assignment.
- `executor.inFlightCount`: assigned queries awaiting completion.

## executor.end

`executor.end() => Promise<void>`

Stops accepting new queries, drains accepted work and closes connections. Repeated
calls return the same shutdown Promise. New queries reject with
`PG_EXECUTOR_CLOSED` and outcome `'not-sent'`. With query deadlines disabled,
graceful shutdown can wait indefinitely for work; use `destroy()` to stop waiting.

## executor.destroy

`executor.destroy(cause?) => Promise<void>`

Stops admission and discards connections. Waiting queries reject with
`PG_EXECUTOR_DESTROYED` and outcome `'not-sent'`; assigned queries reject with
`PG_EXECUTOR_UNKNOWN` and outcome `'unknown'`. The optional cause is retained.
The Promise resolves after connections close. Repeated calls share the shutdown
Promise, and `destroy()` can interrupt an earlier `end()`.
