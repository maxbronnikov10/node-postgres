При одинаковых max 4/depth 16 обычные TCP SELECT всё ещё быстрее у Postgres.js. Большие выборки и UPDATE также не получили общей победы. Настройки по умолчанию и одинаковые бюджеты разделены ниже.

Оптимизация работает в обычном `postgres(url)` без подсказок типов, custom parsers, binary mode или новых флагов. Объектные результаты остаются обычными массивами с прежними readonly/nonenumerable `count`, `command`, `columns`. `.values()` измеряется отдельно и применяется к обоим драйверам.

## Что изменилось

- Ленивый PromiseLike сохраняет однократное выполнение, но передаёт результат через внутренний callback без промежуточного Promise. Внутренние SQL-конфиги и массивы значений не копируются повторно; публичный `QueryExecutor.query()` продолжает проверять и копировать пользовательский ввод.
- Метаданные кешированного statement копируются через `Field`; результаты сохраняют независимые изменяемые описания колонок. Generated decoder читает уже проверенные длины полей побайтно; проверки целостности протокола остаются в protocol parser.
- Короткий SELECT обучает распределитель, если вернул не более одной строки за ≤10 мс от постановки в очередь. Кеш ограничен 256 SQL текстами до 16 KiB, TTL пять минут. Быстрые чтения предпочитают два свободных от обычной работы соединения; при заполнении пары доступен весь пул.
- UPDATE/INSERT RETURNING, транзакции, медленные и многорядные ответы не получают такую привязку. Дефолтный предел остаётся **четыре соединения**, depth 16. Ошибки не повторяются автоматически; каждый независимый statement сохраняет свой Sync и подтверждение коммита.
- Также сохранены ограниченное объединение небольших cached Bind/Execute/Sync в записи до 64 KiB, fast boolean decoding и кеширование parameterless extended SELECT. Большие входные Buffer обходят дополнительное копирование.

Предсказание основано на прошлых выполнениях SQL: резкая смена стоимости параметров может повлиять на следующий пакет, после медленного/широкого ответа запись удаляется. Число соединений и стратегия их использования влияют на результаты.

## Методика

Три независимые VM на каждую группу. Четыре отдельные actor-процесса: два экземпляра каждого драйвера. Восемь раундов по три секунды, прогрев две секунды, порядок акторов сбалансирован вращением. У обеих сторон одинаковые SQL, значения и проверка всех возвращённых полей. Все измерения сохранены при проигрыше или шуме.

## Контроль отказов под смешанной нагрузкой

В основной серии 8208 запросов получили `PG_EXECUTOR_OVERLOADED/not-sent` на двух TCP VM. Все подтверждённые записи совпали с БД; четыре других VM завершили по 900000 операций без ошибок. Это не доказательство стабильной пропускной способности 1500 операций/с без отказов.

[Дополнительный контроль](https://github.com/maxbronnikov10/node-postgres/actions/runs/43754864066): на каждой новой VM два независимых 120-секундных процесса текущего исходника и два предыдущего `613a7c39...`, чередование порядка, одинаковые max 4/depth 16/очередь 256. Параллельно раз в секунду измерены состояния ожидания PostgreSQL. Все прогоны сохранены.

Отказы есть у обоих вариантов, с большим разбросом между повторениями. Во время проблемных прогонов сервер фиксировал `LWLock/WALWrite` и `IO/WalSync`; на VM без отказов такие ожидания редки. Это согласуется с ограничением WAL-пути стенда; точная причина задержек не установлена. Изолированная регрессия нового распределителя этим контролем не подтвердилась. Во всех 12 процессах счётчики БД точно совпали с подтверждёнными изменениями.

`load-control-summary.json`, `control-*.json`, `control-waits-*.json` сохраняют счётчики, latency и числовые состояния ожиданий. SQL-текст, PID, логи и пути окружения исключены.

## Регрессии и отдельная установка

Все десять CI jobs прошли: линтер и девять сочетаний Node.js/PostgreSQL. Покрыты protocol framing, malformed lengths, custom parsers, metadata isolation, result budgets, очереди, дедлайны, резервирование сессии, независимые commit и rollback. Новая регрессия: две серии по 16 UPDATE используют четыре backend и сохраняют ровно 32 изменения.

Локальная проверка блокировок: четыре прогретых backend, короткие чтения используют два; оба они заблокированы обычными запросами на advisory_xact_lock, а 16 чтений завершаются через два оставшихся backend до снятия блокировки. Без доступа к private cache.

Отдельная локальная нагрузка: 180 000/180 000 операций, ноль ошибок/отказов очереди, 21 600/21 600 изменений в БД. Это проверка корректности, не сравнительный замер скорости.

Четыре согласованных tarball установлены в чистый consumer без workspace links. CJS/ESM, восстановление после result budget, binary int4, SQL и транзакция прошли. С запретом генерации кода отдельно проверены mixed object/array, Unicode, bool, JSON, точный int8, memoization, независимые коммиты вокруг ошибки и rollback. Manifest содержит исходный commit, версии и SHA-256 пакетов.

## Отброшенные варианты

Native Promise subclass замедлил полный путь в контролируемой ablation; он не сохранён. Захват parser functions и альтернативные metadata descriptors не дали стабильного выигрыша. Все metadata остаются plain-array с прежними свойствами.

Постоянный default max=2 ускорял короткие чтения только на части VM и ухудшал UPDATE: 0.547–0.637× Postgres.js в полном сравнении против 0.827–0.835× у max=4 предыдущего кандидата (есть шумные ячейки). Это разные запуски VM; данные не изолируют один только эффект размера пула. Этот default откатан. Новый алгоритм сохраняет четыре доступных соединения и ограничивает предпочтение быстрыми короткими SELECT.

В одном длительном прогоне предыдущего кандидата 256 запросов получили PG_EXECUTOR_OVERLOADED/not-sent при скачке очереди; 899744 завершились. Подтверждённые записи точно совпали с БД. Эти промежуточные результаты не включены в итоговые успешные операции нового исходника.

## Повторить и пределы

Весь стенд воспроизводится из immutable source commit через `.github/workflows/benchmark-defaults.yml` и `benchmark-unprepared.yml`. Setup требует disposable DB и пересоздаёт benchmark-таблицы. Профили `postgresjs` и `postgresjs-defaults` сохраняют одинаковые лимиты и реальные API defaults отдельно. Все раунды и samples сохранены в очищенных JSON рядом с summary.json; artifacts.json содержит SHA-256 итоговых файлов и оригинальных Actions artifacts. Сырые ZIP с логами и профилями отклонены автоматической проверкой публикации; в этом новом наборе их нет. Для локальной проверки блокировок: задайте PGHOST, PGPORT, PGUSER, PGDATABASE для disposable DB и выполните `node benchmark/default-scheduler-results-2026-11-15/scheduler-lock-check.cjs`.

Это прогретая синтетическая нагрузка. Реальный production, cold start, WAN, все внешние адаптеры и универсальная победа во всех SQL не проверены. Большие выборки и записи нужно оценивать по таблицам, а не переносить на них выигрыш коротких параллельных SELECT.
