# TypeScript, удобный API и следующие оптимизации

[GitHub run 43658197658](https://github.com/maxbronnikov10/node-postgres/actions/runs/43658197658)
завершился успешно: регрессии, три отдельные VM и установка согласованных пакетов.
Использованы стандартные публичные runners Ubuntu 24.04, по четыре vCPU;
студенческие кредиты не активировались. Успешный job подтверждает выполнение
проверок; качество измерения оценивается отдельно по контрольным повторам.

## Что изменено

Весь runtime пакета `pg`, включая crypto и native-адаптер, перенесён из 19
JavaScript-модулей в `src/*.ts`; `pg-pool` также перенесён на TypeScript.
Включён полный `strict`, в том числе проверка инициализации полей.
`lib/*` сохранены как короткие CJS-входы в скомпилированный runtime.
Декларации поставляются внутри пакетов; обычные импорты, ESM default/named
exports и прежние deep imports сохранены. Отдельный `@types/pg` для этого API
не требуется; стандартные Node types остаются инструментом TypeScript-проекта.

Новые методы позволяют получить строки без ручного извлечения `result.rows`:

```ts
import { QueryExecutor } from 'pg'

interface User {
  id: number
  name: string
}

const db = new QueryExecutor({ connectionString: process.env.DATABASE_URL })
try {
  const user = await db.maybeOne<User>('SELECT id, name FROM users WHERE id = $1', [42])
  const users = await db.rows<User>('SELECT id, name FROM users WHERE active = $1', [true])
} finally {
  await db.end()
}
```

`one()` требует ровно одну строку; `maybeOne()` возвращает строку или `null`;
`rows()` возвращает массив. Неверная cardinality даёт `PG_EXECUTOR_ROW_COUNT`,
`outcome=unknown`, `safeToRetry=false`: SQL уже выполнен, INSERT RETURNING может
быть committed. Повторов запросов нет. Ошибки конфигурации называют конкретный
option. Поддержаны readonly параметры, интерфейсы строк без index signature,
tuple rows и пользовательские парсеры с произвольными OID.
Полный контракт — [API](../docs/pages/apis/query-executor.mdx).

## Методика измерения

Node 22.22.1, PostgreSQL 18.7. Проверены `fsync`, `full_page_writes`,
`synchronous_commit`: все `on`. Таблица обычная logged, один CHECKPOINT перед
executor-фазой вне измерения. На всех вариантах четыре прогретых frontend-
соединения, 16 concurrent запросов, depth 16 у QueryExecutor, pending 1024,
cache подготовки 16. Проверяются все поля всех 500 строк.

Два процесса каждого варианта измеряются последовательно. Позиции четырёх
процессов сбалансированы и записаны в raw JSON. SELECT/500 rows — восемь раундов
по три секунды; UPDATE — восемь по пять; PgBouncer — четыре по три.
Прогрев каждого процесса две секунды.

Коэффициент — медиана попарных head/base. Шум — максимальное отклонение
base2/base и head2/head от единицы, без утверждения о доверительном интервале.
До запуска установлен порог качества 10%. Заметный эффект требует минимум 2%,
превышения шума и одного направления всех раундов.

Array и int4 профили сравнивают один и тот же TS-кандидат. В array-профиле
меняется только представление результата object → array. В int4-профиле
пользовательский `types` override выбирает `Number` только для текстового OID 23;
binary, int8, numeric и все остальные OID используют обычные парсеры.
Это существующие настройки API, изменения default-парсеров нет.

PgBouncer 1.25.2: transaction mode, backend pool 4, prepared tracking 200,
проверенный TLS 1.3 с обеих сторон. Relay задерживает каждый фрагмент минимум
на 3 мс на направление; это стенд, без утверждения о точном WAN RTT.
Новые динамические host ports устранили зависимость fixture от свободного 32774.

эквивалентности на всех нагрузках и не ускорение от самого языка.

Пятисекундный CPU-профиль локального bulk object-сценария, после прогрева:
4186 сэмплов. Крупнейшие self samples: `utf8Slice` 16,29%, Buffer `slice` 9,27%,
`_handleDataRow` 7,98%, `parseDataRowMessage` 7,41%, `parseInteger` 7,36%,
`parseRow` 4,28%, EventEmitter `emit` 3,25%, `_consumeResult` 1,17%.
[Сводка профиля](results/typescript-2026-11-15/cpu-profile.json).
Это доли сэмплов одного диагностического прогона, не прогноз ускорения.

Следующий обоснованный кандидат — бинарный вывод для фиксированного набора
типов, например int4, чтобы уменьшить текстовое декодирование. Для произвольной
схемы такой режим требует проверки семантики каждого binary-парсера и точности
numeric/int8. Его ускорение в этой работе не измерялось. Диспетчеризация DataRow
и построение объектов также остаются кандидатами для отдельного профилирования.

Новый API остаётся для независимых statement; транзакции и session state требуют
эксклюзивного Pool client. Generic описывает ожидаемые поля результата;
TypeScript проверяет обращения к ним, PostgreSQL определяет фактические значения.
Самостоятельные пакеты cursor/connection-string/native не переносились на TS;
их согласованные архивы проверены вместе с новым pg. Автоматические выборы primary,
реальный WAN и production-нагрузка этой работой не проверялись.
