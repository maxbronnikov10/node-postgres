# Нагрузка, SQL-теги и дополнительная оптимизация

SQL-теги необязательны. `QueryExecutor.query(text, values)` и `rows` / `one` /
`maybeOne` принимают обычный SQL с параметрами `$1`, `$2`. Теги удобны для
композиции фрагментов и идентификаторов; сетевой протокол и ограниченный executor
доступны без них.

```ts
import { QueryExecutor } from 'pg'

const db = new QueryExecutor({ connectionString: process.env.DATABASE_URL, max: 4 })
try {
  const row = await db.one<{ id: number }>('SELECT $1::int AS id', [42])
} finally {
  await db.end()
}
```

## Что изменено

Компилятор тегов обходит фрагменты одним циклом. Убраны промежуточные массивы
`flatMap` / `map` / `join`; вложенные параметры получают смещение при рекурсии.
Публичный API, lazy execution и однократное выполнение сохранены. Новых
зависимостей нет.

В двух отдельных локальных CPU-профилях доля `flatten` + `compile` уменьшилась
с 5.66% до 0.53% выборок. Это диагностический результат, а не оценка прироста
throughput: локальный A/B с восемью раундами дал шум 42.1% и признан
неопределённым. Численная сводка CPU-профилей и локальный A/B находятся
в [данных](results/production-2026-11-15/). Сами локальные CPU-профили не публикуются: автоматическая проверка отклонила загрузку из-за приватных путей и метаданных окружения. Они сохранены локально; их выборки сверены с численной сводкой.

все десять заданий прошли — lint и девять сочетаний Node.js 20/22/24/26 с PostgreSQL

вложенные фрагменты, lazy execution, формат результата, cardinality,
commit/rollback и закрытие. Мутация смещения вложенных параметров делает тесты
красными; восстановление исходного compiled JS возвращает все одиннадцать
проверок в зелёное состояние. Скомпилированный файл восстановлен побайтно.

Четыре согласованных архива установлены в отдельный consumer без symlink к
checkout. Проверены CJS/ESM, параметры, tagged SQL, транзакция, binary int4 и
восстановление после превышения бюджета результата. В npm ничего не опубликовано.

Короткие TCP и TLS/PgBouncer прогоны всех API прошли. Переполнение очереди
возвращает `not-sent` / `safeToRetry: true`; после обрыва своего backend исход
выполнявшегося чтения — `unknown` / `safeToRetry: false`, а новое чтение
восстанавливается. Записи автоматически не повторяются.

  `postgres@sha256:1018733457011bf88d81db98cf43aac6d5150afc18787dbe204771fedf80ff95`.
  `fsync`, `full_page_writes` и `synchronous_commit` проверяются как `on`.
- PgBouncer 1.25.2, transaction pooling, четыре backend, tracking prepared
  statements отключён. В этой фазе оба клиента используют `prepare:false`.
- Четыре frontend и глубина pipeline 16. У нашего executor maxPending 256,
  deadline 5 секунд; у Postgres.js эквивалентных ограничений нет. Общий внешний

  20 диапазонов по 20 строк, 8 UPDATE и 2 транзакции по два UPDATE. Это операции
  приложения, не число отдельных SQL statements.
- Проверяется каждое возвращённое поле, включая JSON payload. После drain сумма
  счётчиков в БД должна точно совпасть с числом подтверждённых записей и
  транзакций; обнаруживаются пропуски и дубли.
- Фиксированная интенсивность поступления. Задержка начинается с планового
  момента поступления, включая lag генератора, ожидание в очереди и выполнение.
  Успешные операции, ошибки и отказы внешнего лимита имеют отдельные гистограммы.
  При lag генератор догоняет расписание пачкой; это отражается в задержках.
- TCP: по 120 секунд и 1500 операций/с на tag, query и Postgres.js. Порядок API
  вращается между тремя VM.
- TLS/PgBouncer: 1000 операций/с, relay 3 мс в каждом направлении. Tag — 600
  секунд; query, Postgres.js и явный `sql.typed(value, 23)` control — по 120 секунд.
  Проверяются живые настройки pooler, TLS 1.3 и проверка backend certificate.
- Сохраняются p50/p95/p99/max, CPU, RSS/heap до/после/после GC, десятисекундные
  samples, пики очереди и незавершённых запросов, где API предоставляет метрики.

Отдельный before/after компилятора использует восемь раундов по три секунды,
две секунды warmup и четыре процесса: base, head и по второму процессу того же
кода. Все позиции сбалансированы. Шум выше 10% делает строку неопределённой;
значимый эффект требует всех раундов в одну сторону и величины больше шума и 2%.

## Результаты

Все 4 500 000 предложенных операций завершились успешно: ошибок и отказов
внешнего лимита нет. Во всех 21 фазах сумма счётчиков совпала; подтверждены
540000 инкрементов без пропусков и дублей. Отдельная проверка сверила все 168 числовых ячеек нагрузочных таблиц с исходными JSON.

На двух VM before/after компилятора дал подтверждённые +3.49% и +3.78% RPS.
На первой VM +3.45% не отделились от шума 4.47%; общего гарантированного
прироста для любой машины не заявляем. Все три VM: Intel Xeon 6975P-C, 4 vCPU.

**Теги не нужны для производительности.** В TCP-фазе клиентский CPU на операцию
у tag был на 3.69–6.60% выше query. Разница p99 между этими API меняла направление.
Это наблюдение трёх последовательных фаз со сменой порядка, без отдельных
same-code controls для метрик CPU; его нельзя превращать в универсальный процент
накладных расходов. Для обычного приложения можно выбирать query + параметры,
а теги оставлять для удобной композиции.

**Общего выигрыша над Postgres.js в этой смеси нет.** На TCP Postgres.js потреблял
меньше клиентского CPU и имел меньший p99 на всех трёх VM. Через TLS/PgBouncer
все API выдержали 1000 операций/с с близкими задержками. Явный int4 type control
не меняет этот вывод. Ранее измеренный большой выигрыш unprepared text относится
к другому набору запросов и типов параметров.

Десятиминутный tag soak на каждой VM: 600000 операций, p95 9.887–10.207 мс,
p99 41.215–43.391 мс, пик RSS 99.83–100.13 МиБ. Прирост heap после принудительного
GC относительно старта — 0.177–0.182 МиБ. Это данные клиента, не память PostgreSQL;
такой короткий интервал не доказывает отсутствие долгоживущей утечки. Общий p99
описывает смесь, включая полную транзакцию; раздельные гистограммы по типам
операций не собирались.

Отдельные overload-фазы не входят в эти 4.5 млн операций. В каждой фазе нашего
клиента 192 из 512 запросов отклонены как not-sent; остальные 320 выполнены,
новый запрос после drain успешен. У query наблюдались пределы 256 ожидающих и
64 in-flight. Во всех трёх прямых recovery-проверках исход прерванного чтения
unknown, replay отсутствует, новое чтение успешно.

## Воспроизведение

Требуется отдельная тестовая БД: harness отказывается создавать схему, если имя
БД не начинается с `nodepg_` или `benchmark`. Административное подключение за
PgBouncer задаётся отдельно через `PG_BENCH_ADMIN_PORT` и
`PG_BENCH_ADMIN_DATABASE`; рабочие запросы полностью квалифицируют имена таблиц
и не полагаются на session-local `search_path`.

```sh
node benchmark/production-load-check.js
PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres PGDATABASE=nodepg_load \
  node --expose-gc benchmark/production-load.js --driver tag --seconds 600 --rate 1000 --output load.json
```

Остальные driver: `query`, `postgresjs`, `postgresjs-typed`. Для Postgres.js
задайте `PG_BENCH_POSTGRESJS_MODULE` с путём к установленному `postgres@4.1.1`.
TLS включает `PG_BENCH_TLS_CA`; дополнительные параметры стенда и команды
зафиксированы в [workflow](../.github/workflows/benchmark-production.yml).

## Ограничения

Это изолированная синтетическая OLTP-нагрузка, не копия workload конкретного
боевого приложения и не гарантия production capacity. Фиксированная
интенсивность не определяет максимальную пропускную способность.
Десять минут наблюдений не доказывают отсутствие долгоживущей утечки.
TLS relay не моделирует настоящий WAN, packet loss или холодный failover.
Обрыв backend проверен напрямую; через transaction pooler backend может быть
передан другому клиенту, поэтому эта фаза там явно пропущена.

Полная совместимость с Postgres.js, боевые миграции и 24-часовой soak не проверялись.
Предыдущие сравнения prepared SELECT, bytea и unprepared text остаются
[отдельным историческим снимком](sql-results-2026-11-15.md).
